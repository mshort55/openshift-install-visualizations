# Solution example

This production page illustrates the proposed installation journey for `edge-east`. Its six chapters are independent moments. Chapter navigation does no work and a later sample does not clear an earlier failure. Preparation demonstrates saving and resuming an incomplete plan; Installation compares automated and approved local-BMC boot. Readiness demonstrates targeted customer-hook recovery. Handoff and reuse stay static samples.

`model.ts` owns chapter identities, labels, phases and default outcomes. `preparation.ts` owns the bounded save/resume transitions and displayed plan/outcomes. Its only supplied value is the labelled sample IPAM answer; it cannot run DNS checks or install a cluster. `readiness.ts` owns the two fixed failure/recovery scenes and their evidence. The completed scene includes declared checks, verified cleanup and the handoff together; there is no general execution or status engine. `ui.tsx` owns scene content, controls and disclosures. `links.ts` supplies the selective bidirectional catalog mapping, leaving record normalization to the existing catalog parser. Styles use shared theme tokens beneath `.solution-page`.

`useSolutionSession` retains disclosures, preparation, the two-value boot choice and recovery above page switching. The shared navigation owner captures only source reading state for contextual returns and history; demonstration state is separate from those snapshots, so navigation and Back/Forward never execute or rewind work. No localStorage, sessionStorage or simulation fields belong in routes. Reload and fresh documents use the named chapter’s defaults.

Save works with the API address blank. The saved summary identifies this as a session-only demonstration; Resume retains the supplied answers, checklist and gap. Save/Resume keeps keyboard focus on the same button. Applying the sample moves focus to the read-only API field and announces the change. A later DNS sample uses fixed wording and evidence independently of these controls, with owner wait, publication report and observed lookup kept distinct. General editing, request lifecycle, manual evidence and live rechecks are outside this example.

The technical baseline and samples come from the approved November 2026 design/research. Keep Agent capabilities separate from proposed hub orchestration, customer hook execution separate from content provider, and cluster installation separate from scoped infrastructure readiness. No compatibility certification or live execution is implied.

Boot comparison uses two native buttons with `aria-pressed`, defaulting to automated boot. Selection changes the explanation while preserving `edge-east`, configuration/media r3 and all five hosts. Local boot presents the named Site operations wait followed by illustrative continuation; optional instructions provide the accepted BMC mapping, same media reference, one-time CD/DVD boot and report/evidence to return. The progression keeps media attachment, BMC readback/human reports, observed Agent activity and observed installation completion distinct. Supporting detail separates the three network paths and documented Agent capabilities from the proposed Metal3/Ironic/Redfish integration. Keep automation summarized; step confirmations and additional boot scenarios are outside scope.

Readiness opens with successful installation and a failed customer guest HTTPS hook. One **Show recovery and retry** action explains the repair report, targeted passing job and remaining checks/cleanup. A report alone cannot pass the hook. The result retains earlier successes and failed attempt 881 beside passing 882. Shared evidence components keep the handoff independently readable and consistent with recovery. Technical assumptions, probe contexts and sample run references stay in disclosures. The disappearing recovery control moves focus to the persistent result heading and updates a concise status region. Reading the handoff or changing chapters never performs cleanup or changes recovery.
